# «Огрызки таблиц»: замер вместо догадки (задача 3, 2026-07-28)

Корпус `outout_latin_v2` (722 док., 11 597 таблиц). Воспроизведение:
`python _corpus/measure_table_stubs.py outout_latin_v2`.

## Что утверждалось

> 1 016 таблиц из 11 597 в 379 док. короче 200 символов при низкой плотности:
> **вырезана шапка, тело потеряно**. Понять причину класса (скорее всего bbox
> обрезается раньше тела) и либо восстановить, либо честно исключить.

## Что показал замер

Три независимые проверки, и все три гипотезу не подтверждают.

**A. Критерий по длине ловит не то.** «`raw_text` < 200 символов» даёт ровно те
1 016 таблиц в 379 док., но пересечение с уликами движка — **25 таблиц**:

| | таблиц | документов |
|---|---|---|
| по ДЛИНЕ (`raw_text` < 200) | 1 016 | 379 |
| по УЛИКЕ движка (`low_confidence` детекции или `row_count<=1`) | 866 | 239 |
| пересечение | 25 | |
| **ложно флагнуто длиной** | **991** | |
| **пропущено длиной (улика есть, но длиннее 200)** | **841** | |

Причина проста: плотная числовая таблица укладывается в 200 символов по построению.
`Стадия/T/N/M` на 8 строк — 160 символов; шкала Глазго на 8 строк — 174.

**B. Внутри bbox извлечение ничего не теряет.** Сверка текста области bbox из
текстового слоя PDF с `raw_text` таблицы (сравнение регистро- и скрипт-независимое,
иначе `SaO2` после latin recovery «расходится» с `SаO2` источника):

```
raw_text содержит ВЕСЬ текст своего bbox : 1010 из 1016
теряет                                   :    6   — все шесть в КР627_3/КР898_1,
                                                    документах с битым текстовым
                                                    слоем (в области лежит мусор
                                                    вида `8ga4db8ab9`)
```

Значит «обрезка» — вопрос не дампа, а РАЗМЕРА bbox.

**C. Размер bbox тоже не обрезан.** Для каждой короткой таблицы: продолжаются ли
векторные горизонтальные линии того же x-диапазона ниже нижней границы bbox, и лежит
ли под ней ТАБЛИЧНЫЙ текст (>=2 колоночных зазора >=12pt в строке; считаем по словам —
спаны склеивают строку целиком и зазоров не видно):

```
рамка кончается ровно на bbox                          830
рамка продолжается, но ниже НЕ таблица (проза/сноска)   96
рамка ниже накрыта ДРУГИМ табличным объектом            90   (расщепление на два
                                                              объекта, текст не потерян)
ОБРЕЗКА подтверждена (>=2 табличных строк ниже bbox)      0
```

**Ноль подтверждённых обрезок.** Плюс `row_count<=1` (шапка без тела) — тоже **0**
по корпусу: движок такие уже не выпускает (`TableExtractor._emit_table`, сторож Р2).

## Что сделано

Восстанавливать нечего, исключать из выгрузки — тоже: 991 из 1 016 «огрызков» это
ПОЛНЫЕ маленькие таблицы, и выкинуть их значило бы выкинуть стадирование TNM, шкалы и
дозировки. Исправлен **критерий**, чтобы флаг означал то, что написано на этикетке:

- `synthready.table_is_stub` и гейт `validate._tables_suspect_gate` смотрят на улику
  движка (`low_confidence` — детекция «small», спасённая только подписью сверху; либо
  `row_count<=1`), а не на длину `raw_text`;
- пороги `TABLE_STUB_MAX_CHARS` / `TABLE_DENSITY_MIN` / `TABLE_MIN_FOR_PCT` удалены как
  опровергнутые (I8: держать неиспользуемый порог хуже, чем не иметь его).

удалён, изменилась только пометка.

## Что осталось (замерено, не чинится)

- **90 расщеплений**: одна визуальная таблица извлечена ДВУМЯ объектами (шапка отдельно,
  тело отдельно). Текст не теряется, но модель видит два фрагмента вместо одной
  таблицы. Починка — склейка соседних объектов с общей рамкой; она УМЕНЬШИТ
  `tables_found`, поэтому требует отдельного решения владельца.
- **6 таблиц в КР627_3/КР898_1** с битым текстовым слоем: там теряется не таблица,
  а весь слой документа (эти документы и так в карантине по `corrupt_layer`/`garble`).
