# План: OCR-восстановление как основной метод для проблемных КР

## Обоснование (проверено фактом)
Порча латиницы (HBsAg→НВзА§, Hepatitis→Нераббз) лежит в ТЕКСТОВОМ СЛОЕ PDF (битый toUnicode
у CID-шрифтов Identity-H). Парсер её не создаёт и по тексту починить нельзя. Но глифы
отрисованы верно. Смок-тест: `pdftoppm -r 300` стр.14 КР1_4 → `tesseract` даже с одним `eng`
восстановил HBsAg, HBeAg, Hepatitis B/C virus, IgG, IgM, anti-HCV дословно. С `rus+eng` будут
чисты и кириллица, и латиница. → OCR рабочий, берём как основной.

## Какие файлы идут в OCR-трек (routing)
Из свежего `_corpus/report.json` после валидаторного фикса:
1. §-помеченные (битая латиница при чистой кириллице) — REVIEW по §-сигнатуре (~21).
2. Тотальная глифовая порча (кириллица→ASCII): КР627_3, КР898_1 (sections пустые).
3. SKIPPED_SCAN — сканы без текстового слоя (~21, список в scan_candidates.csv).
4. Прочие REVIEW с реальной порчей текста.
Итого ~44–70 файлов. Точный список даёт report.json (status==REVIEW + cls==SKIPPED_SCAN).

## Конвейер (совместим с пайплайном коллеги: OpenCV/Tesseract + Camelot)
1. Рендер страниц: `pdftoppm -r 300 -png` (или OpenCV: deskew + бинаризация для сканов).
2. Текст: `tesseract -l rus+eng` (ОБЯЗАТЕЛЬНО оба языка — иначе латиница или кириллица уедут).
   Подтверждено: rus+eng читает и русский текст, и латинские аббревиатуры/коды/ссылки.
3. Таблицы: Camelot → JSON (как уже делает коллега), для постпроцессинга.
4. Реконструкция в схему: прогнать чистый OCR-текст через структурный парсер crparser,
   чтобы получить ТУ ЖЕ JSON-схему (metadata+url / sections-дерево / tables / stats).
5. Пере-валидация: `validate.py` на новом JSON → подтвердить PASS и отсутствие §-токенов.

## Два режима (по классу файла)
- **Сканы + тотальная порча** (нет годного текста): полный OCR страницы → структурирование
  с нуля. Иначе никак.
- **§-класс (кириллица чистая, битая только латиница):** быстрее — НЕ перепарсивать всё, а
  восстановить ТОЛЬКО латинские токены: прогнать OCR, взять из него латинские фрагменты и
  подставить на место §-токенов в уже чистом тексте парсера (выравнивание по позиции/контексту).
  Сохраняет хорошую структуру парсера, экономит работу. Если выравнивание сложно — fallback на
  полный OCR+переパарс.

## Контракт вывода
JSON той же схемы, что основной парсер (metadata с url, sections, tables, stats), чтобы
OCR-восстановленные файлы падали в тот же корпус без спец-обработки на стороне потребителя.

## Верификация (без ручного отсмотра каждого)
- После OCR прогнать validate.py: файл должен стать PASS, §-детектор — 0 срабатываний.
- Спот-чек: латинские термины (HBsAg, TNM, Child-Pugh, IgG) читаются; в тексте нет «§»-мусора.
- Сверка покрытия/структуры с исходным рендером на выборке.

## Смок-тест шрифтового извлечения (опционально, для сравнения)
Быстрый эксперимент без OCR: fontTools читает встроенный шрифт, но у этих PDF Identity-H +
subset с битым toUnicode — восстановление Unicode из глифов сводится к сопоставлению контуров
со стандартными формами, т.е. фактически к тому же OCR. Учитывая, что OCR уже даёт чистый
результат, шрифтовой путь низкоприоритетен; при желании — пилот fontTools на КР1_4, чтобы
сравнить точность на латинских токенах.
