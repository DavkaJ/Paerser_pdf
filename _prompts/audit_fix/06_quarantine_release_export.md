# 06. Физический карантин + release-экспортёр с контрактом обучающего корпуса

**Зачем.** Аудит (§1.4, §3.5 п.8, §5.1): «Не исправлять один глобальный threshold — разумно.
Оставлять эти файлы в общей публикуемой директории — неразумно. Сейчас hard quarantine
отсутствует.» Плюс §5.3: неочищенная иностранная библиография допустима в JSON **только
если контракт запрещает использовать `excluded.references` для обучения и экспортёр
физически его не включает**. Сейчас такого enforceable-контракта нет.

Отдельно: `outout_pass/` и `outout_extra_usable/` собирались ручными промптами со списками
имён файлов (`_prompts/assemble_extra_usable.md` содержит явный перечень из 36 КР). Это
ровно тот процесс, который аудит называет непроверяемым.

**Проверено — и это само по себе находка.** В `outout_pass/` лежит **596** файлов, а не 616.
Это множество **не совпадает** с текущим множеством PASS: 21 PASS-файл там отсутствует
(КР401_2, КР205_2, КР408_2, КР571_2, …), а КР875_1 — присутствует, хотя его текущий статус
REVIEW. То есть выгрузка сделана от ДРУГОГО прогона, чем нынешний report.json, и никто не
может сказать, от какого именно. Это ровно тот дефект, который чинят промпты 01 и 05.
Заменяем ручную выгрузку на детерминированный экспортёр, работающий от манифеста прогона,
а не от списка, набранного руками.

```
Задача: FAIL/REVIEW/SKIP физически не могут попасть в обучающий корпус. Экспорт для
обучения — отдельный артефакт с явным контрактом и собственным манифестом.
Новый файл `release.py` в корне. Парсер/валидатор/батч НЕ трогать.

=== ЧАСТЬ 0. Имя директории — не косметика ===
Пока промпт 14 (gold set) не выполнен, ни один документ **не аттестован**. Называть
результат `release/` — значит воспроизвести ровно ту ошибку, из-за которой 596
непроверенных файлов уехали к коллегам как готовые.
Поэтому:
  - до промпта 14 директория называется **`candidate_release/`**, и каждый манифест
    содержит `"attested": false`;
  - переименование в `release/` разрешено ТОЛЬКО после того, как gold-замер выполнен и
    пороги из ЧАСТИ 2-bis пройдены на holdout.
Это единственная защита от того, чтобы «кандидат» снова стал «релизом» по умолчанию.

=== ЧАСТЬ 1. Карантин ===
После публикации батча (промпт 05) раскладывать выходы по статусу:
  candidate_release/  — только PASS (до промпта 14; затем release/)
  quarantine/ — FAIL, REVIEW, SKIP; внутри подпапки по ПРИЧИНЕ (kind):
      quarantine/COLLAPSE/, quarantine/OCR_REQUIRED/, quarantine/RESIDUAL_PIN/,
      quarantine/TOC/, quarantine/SCHEMA/, quarantine/CRASH/ ...
      **quarantine/UNVERIFIABLE_OCR/** — отдельная обязательная категория, найдена при
      исполнении промпта 03: **24 документа-скана, восстановленных ПОЛНЫМ OCR**
      (`total_chars` 39-513 тыс., 13-56 секций), у которых `parse_toc` перечитывает
      исходный PDF БЕЗ полного OCR, видит пустой текстовый слой и не может извлечь
      оглавление -> `TOC_NONE`.
      Это значит: **парсер и валидатор смотрят на разные документы.** Структура этих
      файлов не проверена против источника ни разу. Они целиком произведены OCR и
      являются самыми рискованными в корпусе.
      Правило: `UNVERIFIABLE_OCR` не может попасть в обучающий корпус **ни при каком
      статусе**, пока промпт 16 (единый `DocumentView`) не устранит двойное чтение PDF.
      Это не «плохие данные» — это данные, о качестве которых мы не имеем права судить.
      Файл с несколькими причинами кладётся в папку ПЕРВОЙ по severity
      (FAIL > REVIEW), а полный список причин пишется в quarantine/index.json.
Раскладка — жёсткими ссылками или копией, но НЕ перемещением (outout/ остаётся полным
сырым выходом). Обе директории — в .gitignore.

`quarantine/index.json`: {"КР848_1": {"status": "REVIEW", "kinds": ["COLLAPSE", "OVERCOUNT"],
"first_seen_run": "<run_id>"}, ...} — чтобы было видно, что именно чинить и сколько файлов
разблокирует каждый фикс.

    "exclude": ["excluded.references", "excluded.toc", "excluded.front_matter",

    "rationale": {

         Karnofsky), критерии оценки качества и алгоритмы — клинически ценный контент.

         mixed-script детектор ОБЯЗАНЫ покрывать эту зону (промпт 04), а coverage не

      "excluded.toc": "оглавление/сокращения/термины склеены, границы регионов неверны",
      "excluded.other": "мусорная корзина сегментера, содержимое не аттестовано"
    },
    "require_status": ["PASS"],

    "require_thresholds": {                   // см. ЧАСТЬ 2-bis

    }
  }

=== ЧАСТЬ 2-bis. Обязывающие пороги релиза (§6.4 п.4 аудита) ===
Аудит требует не только гейтов, но и ЧИСЛОВЫХ порогов, которые релиз обязан выполнить:
section recall/precision, structured coverage/overlap, numeric/unit/Latin exactness,
table cell recall/precision, zero clinically material corruption in release sample.
Пока промпт 14 (gold set) не выполнен, этих чисел не существует — и это надо признать
явно, а не замолчать:
  - до промпта 14: `require_thresholds` пуст, а RELEASE_MANIFEST и README **обязаны**
    содержать пометку `"attested": false` и фразу «корпус не аттестован против gold set».
  - после промпта 14: `require_thresholds` заполняется реальными числами, экспортёр
    ОТКАЗЫВАЕТСЯ собирать релиз, если замер на gold-holdout их не выполняет.
    Стартовый набор порогов (уточнить по факту замера):
      section_recall >= 0.95, heading_assignment_accuracy >= 0.95,
      table_cell_f1 >= 0.90, numeric_exactness >= 0.99,
      critical_span_exactness >= 0.995 (ICD/TNM/ATC/дозировки — почти нулевая
      терпимость: одна испорченная дозировка дороже сотни опечаток),
      duplication_rate == 0.
`"attested": false` — это не формальность. Именно отсутствие такой пометки на предыдущей
выгрузке привело к тому, что 596 непроверенных файлов ушли к коллегам как готовые.

=== ЧАСТЬ 2-ter. Ручная проверка выборки — БЛОКИРУЮЩИЙ гейт (§6.4 п.6 аудита) ===
Аудит требует шестым условием ненулевой готовности: «вручную проверить стратифицированную
выборку PASS и все boundary cases». Ни автоматический гейт, ни gold set этого не заменяют:
gold проверяет метрики, а человек ловит то, для чего метрики не придуманы.
Реализация как ГЕЙТА, а не как пожелания:
  - `release.py --sample <run_id>` формирует стратифицированную выборку: 30 документов
    PASS (по стратам из промпта 14: канал текста, размер, нумерация, таблицы) + **все**
    boundary cases (файлы, прошедшие гейт с запасом <10% от порога — их список
    вычисляется, а не назначается);
  - выборка выкладывается в `candidate_release/<run_id>/_manual_review/` вместе с
    чек-листом (`REVIEW_CHECKLIST.md`): структура разделов, таблицы, коды МКБ/TNM/ATC,
    дозировки, отсутствие кирилло-латинской порчи в теле;
  - результат ревью пишется человеком в `_manual_review/verdict.json`:
    `{"reviewed_by": "...", "reviewed_at": "...", "documents": {"КРxxx": "ok"|"defect: ..."}}`;
  - **экспортёр ОТКАЗЫВАЕТСЯ собирать финальный релиз, если `verdict.json` отсутствует,
    не покрывает всю выборку, или содержит хоть один `defect`.** Найденный дефект =
    гейт пропустил класс ошибок = чинить гейт, а не выкидывать документ.

=== ЧАСТЬ 3. Экспортёр ===
`python release.py --run <run_id>`:
  1. Читает `_runs/<run_id>/run_manifest.json`. Без манифеста — отказ.
  2. Проверяет `run_integrity_ok == true` (см. промпт 05). Иначе — отказ, экспорта нет.
     Замечание: `quality_gate_ok == false` экспорту НЕ мешает — экспортёр сам отбирает
     только PASS. Он блокируется именно нарушенной ЦЕЛОСТНОСТЬЮ прогона.
  3. Отбирает документы со статусом из `require_status`.
  4. Для каждого — строит ОБУЧАЮЩИЙ JSON по контракту: включает только разрешённые
     разделы, физически ВЫРЕЗАЯ запрещённые. Результат — в `release/<run_id>/`.
  5. Проверяет `require_zero`: документ с ненулевой порчей в экспорт НЕ попадает,
     даже если у него статус PASS (двойная страховка поверх гейта 04).
  6. Пишет `release/<run_id>/RELEASE_MANIFEST.json`:
       run_id, code/env/config, contract_version, число документов, sha256 каждого
       экспортированного файла, счётчики, и ЯВНЫЙ дисклеймер о том, что корпус НЕ
       аттестован против gold set (пока не выполнен промпт 14).
  7. Пишет `release/<run_id>/README.md` для получателя: что внутри, что вырезано и почему,
     какие известные дефекты остаются, чего НЕЛЬЗЯ делать с этими данными.

=== ЧАСТЬ 4. Ретро-уведомление по уже отгруженному ===
Сгенерировать `_corpus/RECALL_NOTICE.md` по факту, а не по памяти:
  1. Прочитать РЕАЛЬНОЕ содержимое `outout_pass/` (596 файлов) и `outout_extra_usable/`
     (83 файла) — не полагаться на «там должны быть PASS».
  2. Сверить с текущим report.json: какие из отгруженных файлов больше не PASS по новым
     гейтам (03+04), с причиной по каждому.
  3. Отдельным разделом — **рассинхрон самой выгрузки**: 21 PASS-файл, которого в
     `outout_pass/` нет, и КР875_1, который там есть при статусе REVIEW. Это доказательство
     того, что выгрузка делалась от неизвестного прогона.
  4. Отдельно: отгруженные файлы содержат `excluded.references` с exact-token attestation
     43-50% (замер аудита) — по новому контракту они из обучения исключены. Коллеги должны
     знать, что эти поля использовать нельзя.
Документ для коллег. Не отправлять автоматически — показать заказчику.

=== ГРАНИЦЫ ===
- Новые файлы: release.py, crparser/data/training_contract.json.
- НЕ менять: парсер, валидатор, батч, схему выходного JSON.
- Экспортёр НЕ «чинит» данные. Он только фильтрует и вырезает. Любая правка контента —
  вне его полномочий.
- Никаких списков имён файлов, набранных руками. Всё — от статуса и манифеста.

=== ТЕСТЫ-ПИНЫ ===
- Экспорт без манифеста -> отказ, exit != 0.
- Экспорт при `run_integrity_ok == false` -> отказ. При `quality_gate_ok == false`, но
  целом прогоне -> экспорт идёт (отбираются только PASS).
- Отсутствие `_manual_review/verdict.json` -> отказ собрать финальный релиз.
  Хотя бы один `"defect: ..."` в вердикте -> отказ + указание, какой гейт это пропустил.
- До промпта 14 директория называется `candidate_release/`, манифест содержит
  `"attested": false`. Попытка назвать её `release/` без gold-замера -> отказ.
- В candidate_release/ нет ни одного файла со статусом FAIL/REVIEW/SKIP.
- В candidate_release/ ни в одном файле НЕТ ключа `excluded.references`,
  `excluded.toc`, `excluded.front_matter`, `excluded.other` и нет `stats`.
  **`excluded.appendices` — ЕСТЬ** (см. правку контракта ниже).
- КР848_1, КР401_2, КР396_4, КР1_4 в release/ отсутствуют (после 03+04 они не PASS).
- quarantine/index.json содержит все не-PASS файлы, сумма по папкам == число не-PASS.
- RECALL_NOTICE.md непуст и содержит как минимум КР848_1, КР401_2, КР396_4, КР1_4,
  КР720_2, КР502_2, КР957_1, КР609_2. Число файлов в `outout_pass/` доложено как ФАКТ
  (ожидается 596, не 616) и рассинхрон с множеством PASS зафиксирован.
- До выполнения промпта 14 каждый RELEASE_MANIFEST содержит `"attested": false`.
- Повторный запуск экспорта на том же run_id даёт байт-в-байт тот же результат и те же
  sha256 в RELEASE_MANIFEST.
```
