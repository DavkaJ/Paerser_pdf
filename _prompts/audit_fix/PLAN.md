# План исполнения: закрытие технического аудита от 11.07.2026

Мастер-документ. Каждый пункт аудита имеет промпт-владельца. Промпты исполняются
**строго по порядку**: каждый следующий опирается на инварианты, установленные
предыдущим. Порядок выбран так, чтобы сначала перестать врать себе (гейты и
воспроизводимость), потом перестать терять данные (недеструктивность), потом
чинить качество текста, и только затем менять стек.

## Жёсткие инварианты на весь проект

1. **Схема JSON — только аддитивно.** Новые поля добавлять можно; существующие поля
   (`metadata`, `sections[].number/title/level/text/children`, `tables[].page/number/
   caption/raw_text/bbox`, `excluded`, `stats.coverage_percent`, …) сохраняют имя,
   тип и семантику. Downstream-потребители (коллеги, у которых уже лежат
   `outout_pass/` и `outout_extra_usable/`) не должны сломаться.
2. **Ни один промпт не коммитит, если сломан регресс-набор** из `07`.
3. **Никаких хардкодов имён файлов КРxxx** в продуктовом коде. Имена КР допустимы
   только в тестах и в тексте промптов как эталоны.
4. **Сообщения коммитов — по существу**, без упоминания AI/Claude и без
   `Co-Authored-By`.
5. **Все пороги — именованные константы** с комментарием о том, на каком замере они
   получены.

## Gate-критерии перехода между фазами

**A → B.** Существует `_corpus/baseline_manifest.json` с sha256 всех 722 входных PDF,
всех 722 выходных JSON, кода (git SHA + hash дерева `crparser/`), `ocr_pins.json` и
конфигом. Повторный прогон на неизменном входе даёт тот же манифест.

**B → C.** Все пункты выполнены одновременно:
- `КР848_1`, `КР401_2`, `КР396_4` — **не PASS**;
- `validate.py` возвращает ненулевой exit при наличии REVIEW; батч различает три кода
  (0 = чисто, 1 = есть FAIL/REVIEW, 2 = нарушена целостность прогона);
- ни один FAIL/REVIEW/SKIP физически не лежит в `candidate_release/`;
- регресс-набор зелёный; D-тесты из `07a`, закреплённые за промптами 02–06, переведены
  из xfail в passed;
- `ocr_pins.json` не изменяется во время прогона (хеш до/после).

**Важно про пороги фазы B.** Все гейты 03/04/10 — **triage**, а не аттестация. До промпта 14
ни один документ не аттестован, директория называется `candidate_release/`, манифест несёт
`"attested": false`. Право называть результат релизом даёт только gold-замер.

**C → D.** Сумма `included+excluded+tables` больше не может превышать источник:
новая метрика `source_union_coverage` считается по span-ID, `overlap_chars` выводится
отдельно и у `КР848_1` строго > 0. Ни одна таблица не вычитается из текста, если её
`raw_text` пуст или не прошёл reconcile.

**D → E.** Размечен стратифицированный gold set (30–50 документов, ~1 000 страниц) с
двойной span-level разметкой клинически значимых полей; харнесс метрик выдаёт для текущего
пайплайна числа по section recall/precision, table cell F1, numeric/unit/Latin
exactness. **Без этих чисел менять стек запрещено** — иначе нечем доказать, что новый
стек лучше.

## Гейт латиницы (13b) — и почему он НЕ циклический

13b физически стоит перед 14, но его **включение** зависит от 14. Это не цикл, а два разных
события:

1. **Реализация 13b** — сразу после 13, **за feature flag** (`--latin-recovery`, по
   умолчанию ВЫКЛЮЧЕН). Флаг существует именно для того, чтобы код можно было написать и
   померить до появления gold.
2. **Включение по умолчанию и допуск в release** — только после 14: critical span exactness
   на holdout >= 0.995, false-correction rate <= 0.001 (латиница) и <= 0.0005 (кириллица).
   До этого результаты 13b не участвуют в отборе документов для обучения.

**Зависимости 13b:** 02 (immutable pins) + 08 (SourceSpan с кандидатами — иначе негде
хранить альтернативы) + 13 (font-repair как канал E1, и его пилот задаёт ОБЪЁМ 13b).

**Первый шаг 13b — замер остатка, а не код.** Если после 13 остаётся <5% дефектов и они
не критические — контур разметки избыточен, этап сокращается до eng-OCR и гейта. Строить
Label Studio под задачу, которой уже нет, — худший исход.

**Контур разметки 13b и gold set 14 — ОДИН проект Label Studio, один формат, одни люди.**
Не строить два: это двойная оплата одной и той же ручной работы.

**Release-требование (новое, его не было ни в одном промпте):**
> Документ не попадает в обучающий корпус, если в обучаемой зоне (metadata, sections,
> tables, excluded.appendices) остаётся хотя бы один неразрешённый **критический**
> латинский span. Некритические — warning, не блокируют.

**15 и 16 обязаны учитывать результаты 13b:** challenger сравнивается с пайплайном, где
latin recovery уже работает (иначе сравнение нечестное), а роутер выбирает канал с учётом
E1/E2-доказательств.

## Что НЕ входит в план

- Автоматическая «агрессивная» коррекция русских слов (`преимупцество` → …). Аудит прав:
  детектировать и метить — да, автозаменять — нет.
- Полная перезаливка корпуса коллегам до прохождения gate B→C.

## Регламент исполнения каждого промпта

**Промпт — это гипотеза о коде, написанная до его чтения.** Каждое исполнение возвращает
информацию, которой раньше не существовало. Поэтому:

0. **Прочитать `INVARIANTS.md`.** Это накопленные находки предыдущих промптов. Всё, что там
   написано, уже стоило кому-то ошибки.
1. Прочитать промпт целиком, включая «ГРАНИЦЫ». Промпты переписываются — читать **с диска**,
   не по памяти.
2. Реализовать. Не выходить за перечисленные файлы.
3. Прогнать регресс-набор (после `07a` — обязательно) и тесты-пины из промпта.
4. **Проверить контрольную группу I1** (`КР802_1`, `КР845_1`, `КР901_1`, `КР1000_1`,
   `КР66_4`, `КР876_1`). Утоплен хоть один — чинить правку, а не двигать порог.
5. Прогнать корпус там, где промпт требует, и разложить дельту статусов **по причинам**.
   Дельта, которую нельзя объяснить, — не коммитить.
6. **Дописать в `INVARIANTS.md`** всё, что оказалось не так, как ожидал промпт: неверные
   предположения о коде, новые ложные PASS, скрытые зависимости, средозависимое поведение.
   **Находка, не записанная туда, считается потерянной** — следующий промпт наступит на неё
   снова.
7. Коммит одним осмысленным сообщением.
