# 00. Кэш parse_toc: перестать читать каждый PDF дважды

**Зачем — и почему это окупается немедленно.**

```
batch_report.py:68 →  rep = validate_doc(base + ".pdf", doc, parse_toc(pdf))
validate.py:207   →  def parse_toc(pdf_path):
                         reader = PdfReader(pdf_path)
                         pages = reader.read()          # ПОЛНОЕ layout-чтение всего PDF
```

Строкой выше `_PARSER.parse(pdf)` уже прочитал этот же PDF целиком. Итого **каждый прогон
читает 57 681 страницу дважды**. Аудит отметил это в §1.5; промпт 16 чинит радикально
(единый `DocumentView`), но он в самом конце плана.

А пересборка `report.json` понадобится ещё много раз: промпт 04 (структурные гейты),
10 (coverage v2), 11b (монотонность номеров), 12 (три отдельных фикса content-start).
Каждый раз — лишний полный проход по корпусу.

Оглавление зависит **только от содержимого PDF** и не зависит от кода валидатора. Значит
его можно закэшировать один раз и переиспользовать через все правки гейтов.

Это не архитектурное решение, а временная мера до промпта 16. Она того стоит: цена — около
получаса, экономия — часы на каждой итерации гейтов.

---

```
Задача: закэшировать результат parse_toc по содержимому PDF. Логику разбора оглавления
НЕ менять — результат обязан быть идентичным.

=== РЕАЛИЗАЦИЯ ===
- Кэш на диске: `crparser/data/toc_cache/<pdf_sha12>_<toc_code_sha8>.json`.
  - `pdf_sha12` — первые 12 символов sha256 файла PDF. Функция уже есть (промпт 02 /
    manifest.py) — переиспользовать, не писать вторую.
  - `toc_code_sha8` — короткий хеш кода, влияющего на разбор оглавления: содержимое
    `crparser/engine/toc.py` + функции `parse_toc`/`Toc`/`_TOC_ANCHOR`/`_NUM_RE` из
    validate.py. Так кэш **автоматически инвалидируется**, когда промпт 03 или 04 меняет
    правила разбора TOC (например, добавляет римские номера) — и мы не получим устаревшее
    оглавление молча.
- Содержимое кэш-файла: сериализованный `Toc` — `entries` (список пар номер/заголовок) и
  `body_norm`. Оба поля уже есть в классе.
- `parse_toc(pdf_path)`: попадание в кэш -> собрать `Toc` из JSON, PDF не открывать вообще.
  Промах -> прочитать как сейчас, записать кэш (атомарно: temp + fsync + os.replace).
- Директорию `crparser/data/toc_cache/` — в .gitignore (рядом с `ocr_cache/`).
- Флаг `--no-toc-cache` для отладки.

=== ГРАНИЦЫ ===
- НЕ менять логику разбора оглавления: ни `parse_entries`, ни `toc_bounds`, ни якоря.
- НЕ трогать парсер, сегментер, таблицы, OCR.
- НЕ вводить единый DocumentView — это промпт 16. Здесь только кэш.
- Кэш не должен переживать смену правил разбора TOC. Если сомневаешься — включай больше
  кода в `toc_code_sha8`. Лучше лишний пересчёт, чем устаревшее оглавление.

=== ТЕСТЫ-ПИНЫ ===
- ГЛАВНЫЙ: `report.json`, пересобранный С кэшем и БЕЗ кэша (`--no-toc-cache`), совпадает
  **байт-в-байт**. Если нет — кэш меняет поведение, откатывать.
- Первый прогон наполняет кэш; второй — не открывает ни одного PDF (проверить счётчиком
  вызовов `PdfReader.__init__` или профайлером).
- Замерить и доложить: время пересборки report.json до и после. Ожидается сокращение
  примерно вдвое.
- Изменение `_NUM_RE` в validate.py (например, добавление римских номеров в промпте 03)
  -> `toc_code_sha8` меняется -> кэш инвалидируется -> оглавления пересчитываются.
  **Проверить это явно**: иначе промпт 04 будет работать со старым разбором TOC и римские
  номера не появятся.
- Подмена содержимого PDF при том же имени -> кэш не переиспользуется.

=== РЕГЛАМЕНТ ===
1. Реализовать, прогнать пересборку report.json дважды, сверить байт-в-байт.
2. Доложить выигрыш по времени.
3. Коммит: «Кэш разбора оглавления по содержимому PDF (временно, до единого DocumentView)».
```
