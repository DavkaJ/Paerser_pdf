# 15. Challenger POC: Docling / PaddleOCR / Surya против текущего стека на gold set

**Предусловие, без которого промпт НЕ ЗАПУСКАТЬ: выполнен промпт 14 и есть baseline-числа
текущего пайплайна на gold set.** Без них сравнение вырождается в «на глаз лучше».

**Позиция аудита, с которой я согласен:** «Не заменять весь pipeline одним продуктом».
PyMuPDF — хороший baseline для born-digital, он честно извлекает то, что закодировано;
ошибка проекта была не в выборе библиотеки, а в архитектуре доверия. Поэтому это POC на
замену **компонентов**, а не миграция.

**Отдельно.** Если промпт 13 (font-repair) дал >80% восстановления, часть проблем, ради
которых зовут Docling/PaddleOCR, уже решена дешевле и детерминированнее. Перед началом POC
пересмотреть: **что именно мы всё ещё не умеем?** Возможно, ответ — только таблицы. Тогда
POC сужается до table-моделей, и это экономит недели.

=== ШАГ 1. Кандидаты и что именно с них берём ===
| Кандидат | Что тестируем | Риски, зафиксированные аудитом |
|---|---|---|
| **Docling** (standard + hybrid) | детерминированный parse + neural table structure; hybrid с `force_backend_text=True` сохраняет backend-текст | не знает структуру российских КР — профиль всё равно нужен |
| **PaddleOCR PP-StructureV3** | layout + table/formula recognition + reading order | тяжёлый runtime; лучший throughput требует GPU; русский нужно проверять отдельно |
| **Surya** | OCR/layout/order/table, 90+ языков | GPU; лицензия весов — проверить ДО замера |
| **Marker** | PDF→JSON, таблицы/формы | **GPL-код + отдельная лицензия весов — юридическая проверка ОБЯЗАТЕЛЬНА до внедрения**, не после |
| **LlamaParse** | agentic OCR, multi-page tables | cloud/vendor, конфиденциальность мед. данных; 10 000 free credits ≈ 1 000 стр = 1,7% корпуса. **Только как exception-канал, не как основной batch** |
| **LiteParse** | быстрый local PDFium parse, bbox, complexity routing, подключаемый OCR | heuristic Markdown; плотные/многостраничные таблицы — слабое место, то есть ровно наша боль. Мерить только как fast baseline/router, не как решение таблиц |
| **EasyOCR** | простая замена OCR-движка, кириллица, CPU/GPU | нет layout/table pipeline вовсе. Мерить ТОЛЬКО как OCR-baseline против Tesseract; переход без выигрыша по метрикам не обоснован |
| **GROBID** | — | **Отклонить сразу.** Его же FAQ говорит: иерархия разделов надёжно не различается, ячейки таблиц не извлекаются. Тратить время на замер не нужно |

Обязательно: **лицензионная проверка ДО замера**, а не после. Медицинский корпус +
GPL-код + вопросы к весам моделей = риск, который дешевле снять на входе.
Для LlamaParse отдельно: **проверить, допускает ли политика проекта отправку медицинских
документов Минздрава во внешнее облако.** Если нет — исключить, не замеряя.

=== ШАГ 2. Протокол замера ===
- Прогнать каждого кандидата на gold set (dev), привести выход к общему промежуточному
  виду (страницы/строки/таблицы), прогнать `gold/evaluate.py`.
- Сравнивать **по стратам**, а не в среднем. «Лучше в среднем» может означать «сильно
  лучше на чистых, сильно хуже на битых».
- Метрики решения (из промпта 14): section recall/precision, heading assignment accuracy,
  **table cell F1**, numeric/unit exactness, **critical span exactness**, mixed-script rate.
- Замерить также **стоимость**: страниц/минуту на CPU и на GPU, пиковую RAM. На 57 681
  странице разница между 2 и 20 стр/мин — это разница между ночью и неделей.
- Финальную проверку победителя — на **holdout**, один раз.

=== ШАГ 3. Решение ===
Отчёт `_corpus/challenger_report.md`:
  - таблица метрик по стратам, все кандидаты + текущий baseline;
  - throughput и требования к железу;
  - лицензионный вывод;
  - **явная рекомендация**: что берём, на какую роль, что оставляем.
Возможные (и равно допустимые) исходы:
  а) «Берём neural table structure из Docling ТОЛЬКО для таблиц, остальное оставляем» —
     я считаю этот исход наиболее вероятным по имеющимся данным;
  б) «Docling hybrid как основной, профиль КР поверх» — если он выигрывает по всем стратам;
  в) «Никто не выигрывает достаточно, чтобы окупить миграцию» — **это тоже валидный
     результат.** Если 13 дожал font-repair, а 09 починил таблицы, менять стек может быть
     нечего. Не стесняться такого вывода.

=== ГРАНИЦЫ ===
- POC живёт в отдельной ветке / отдельной директории. **Продуктовый пайплайн в этом
  промпте не меняется.**
- Не внедрять победителя в этом же промпте. Внедрение — промпт 16.
- Не сравнивать по «общему OCR score». Это метрика, по которой все выглядят прилично и
  которая ничего не говорит про `D37.6` → `037.6`.
- VLM по рендеру — только как adjudication/exception-канал, НИКОГДА как неоспоримый
  источник. Галлюцинация в дозировке препарата дороже любой экономии.

=== ТЕСТЫ-ПИНЫ ===
- Каждый кандидат прогнан на ВСЕЙ dev-выборке, а не на 2 файлах.
- Отчёт содержит числа по каждой страте; ни одна страта не пропущена.
- Лицензионный раздел заполнен для КАЖДОГО кандидата, попавшего в замер.
- Победитель проверен на holdout ОДИН раз, и это число — в отчёте.
- Рекомендация содержит явную цену внедрения в днях и явный список того, что мы теряем.
