# 04. Структурные гейты: схлопывание, канонический recall, needs_ocr, mixed-script

**Зачем.** Промпт 03 сделал валидатор честным механически (схема, exit, stats). Но он всё
ещё не умеет сказать «структура документа развалилась». Аудит (§3.3) даёт три
подтверждённых ложных PASS, и все три проходят даже честный 03, если не добавить
семантические гейты.

**Доказательства (проверены на корпусе).**

- `КР848_1`: 1 секция на весь документ, `coverage=100`, **ноль warnings**. Единственная
  секция названа «XII. Критерии оценки качества», а её текст НАЧИНАЕТСЯ со слов
  «XIII. Список литературы» — то есть в один узел свалено всё, что после главы XII.
  `excluded.other` — 834 элемента.
- `КР401_2`: 3 секции (1.1, 1.3, 1.4), внутри текста 1.4 лежат заголовки 1.5, 1.6 и глава 2.
  `coverage=99.83`. В тексте упомянуто 15 номеров таблиц, извлечено 0.
- `КР396_4`: PASS при `needs_ocr=1`; в JSON остаются `АтзЮгбат`, `Мапбагб`, разрушенные
  названия генов.
- Корпусный замер (мой, независимый): файлов, где одна секция держит >60% всего текста
  разделов при >3 секциях — четыре: `КР973_1` (0.77), `КР953_1` (0.75), `КР205_2` (0.68),
  `КР246_3` (0.61). Класс узкий, но реальный.

Задача: добавить в validate.py семантические гейты структуры. Пять независимых проверок.
Каждая — с именованным порогом и комментарием о замере. Парсер НЕ трогать.

=== ГЕЙТ 1. COLLAPSE — структура схлопнулась ===
Триггеры (любой -> REVIEW, kind="COLLAPSE"):
  (а) sections_found <= 3 при total_chars > 20 000. Документ КР такого размера физически
      не может иметь 3 раздела. Проверено: срабатывает ровно на КР848_1 (1) и КР401_2 (3).
  (б) доля текста крупнейшей секции от included_chars > 0.60 при sections_found > 3.
      Проверено: КР973_1/КР953_1/КР205_2/КР246_3. Порог 0.60 даёт 4 файла; не занижать
      ниже 0.55 — начнёт цеплять короткие легитимные КР.
  (в) внутри text любой секции найден паттерн заголовка следующего уровня — то есть
      «заголовки внутри текста». Искать НЕ регуляркой по всему тексту (шумно), а так:
      если в text секции с номером N встречается строка, начинающаяся с номера N+1 /
      следующего канонического номера И далее идёт >200 символов — это несобранный
      заголовок. Это ловит КР401_2 (в 1.4 сидят 1.5, 1.6, глава 2).

=== ГЕЙТ 2. CANONICAL_RECALL — потеряны канонические главы ===
Профиль КР знает канонические главы 1-7 + «Критерии оценки качества» (+ римские аналоги
I-VII/XII у части документов). Проверка: сколько из них представлено в дереве секций.
  - recall < 5/7 -> REVIEW (kind="CANONICAL_RECALL").
  - recall == 0 при непустом тексте -> FAIL.
Важно: список канонических глав брать ИЗ ПРОФИЛЯ (profile), не хардкодить в validate.py.
Если валидатор не имеет доступа к профилю — прокинуть его, но НЕ дублировать константы.

=== ГЕЙТ 3. OCR_REQUIRED — needs_ocr никогда не corpus-ready ===
  - `stats.corruption.pseudo_ascii_tokens > 0` ИЛИ `glyph_tokens > 0` ИЛИ в warnings есть
    признак «нужен OCR / OCR не выполнен» -> файл НЕ может быть PASS. -> REVIEW,
    kind="OCR_REQUIRED".
  - Проверено: КР396_4 сейчас PASS при needs_ocr=1.

=== ГЕЙТ 4. MIXED_SCRIPT — остаточная кирилло-латинская порча в ТЕЛЕ ===
Текущий §-детектор (из fix_validator_honesty) ловит только сигнатуру «§ внутри токена».
Добавить второй, узкий и точный детектор — по СЛОВАРЮ ПИНОВ, а не по общей эвристике:
  - взять ключи активной базы ocr_pins (после промпта 02 она вычищена);
  - нормализация ровно как в `ocr_pins.anchor_hit`: strip(_PUNCT), lower, len>=3;
  - считать точные попадания по ТРЁМ зонам раздельно (аудит §3.5 P0-5 требует все четыре
    области; `excluded.appendices` нельзя терять — приложения содержат шкалы и критерии,
    которые идут в обучение):
      ТЕЛО      = sections + tables + metadata + excluded.appendices
      БИБЛИО    = excluded.references
      СЛУЖЕБНОЕ = excluded.toc + excluded.front_matter + excluded.other
  - >=1 попадание в ТЕЛЕ -> REVIEW (kind="RESIDUAL_PIN"). Попадания только в БИБЛИО или
    СЛУЖЕБНОМ -> warning, не REVIEW (эти зоны вырезаются контрактом, см. 06).
  Замер (перепроверен мной): 1 156 точных попаданий всего; 39 в sections/tables у 9
  PASS-файлов; 1 074 — в references; 21 PASS содержит >=2 разных ключа.
  Ожидаемо: ~9 файлов PASS -> REVIEW. Эталоны для теста: КР1_4 (Вагсе1опа, СНшс, ВСЬС),
  КР720_2 (Еигореап), КР502_2 (Сгоир, А1СС), КР957_1 (УЕСР), КР609_2 (погта1),
  КР325_2, КР332_2, КР396_4, КР8_2.
- ШИРОКИЙ mixed-script детектор (кириллица+латиница в одном слове) как САМОСТОЯТЕЛЬНЫЙ
  триггер REVIEW НЕ использовать: аудит замерил 304 слова в 142 PASS, и часть из них —
  легитимные. Выводить его результат ТОЛЬКО как warning с числом, для триажа.

=== ГЕЙТ 5. TABLES_SUSPECT — таблица заявлена, но пуста ===
  - **TABLE_STUB.** Первоначальный критерий («bbox > 15% площади страницы») НЕРЕАЛИЗУЕМ:
    размеров страницы в JSON нет, есть только bbox таблицы. Правильный критерий — по
    площади самого bbox и по отношению к документу, без внешних данных:
      площадь bbox = (x1-x0) * (y1-y0);
      плотность = len(raw_text) / площадь bbox.
    Триггер: `len(raw_text) < 200` И плотность ниже 10-го перцентиля плотностей таблиц
    ЭТОГО ЖЕ документа (крупный bbox, мало текста = вырезали шапку, тело потеряли).
    Если в документе <3 таблиц — перцентиль не считать, использовать абсолютный порог
    плотности TABLE_DENSITY_MIN, откалиброванный по корпусу.
    -> warning (kind="TABLE_STUB").
    Замер: 938 из 9 305 таблиц PASS-корпуса имеют raw_text < 200 символов; медиана по
    корпусу — 672; пустых raw_text нет. То есть отказ проявляется как УСЕЧЕНИЕ.
    **Перед фиксацией порога — посчитать распределение плотностей по корпусу и показать
    перцентили.** Порог, взятый из головы, здесь бесполезен.
  - в тексте секций упомянуто больше уникальных номеров таблиц, чем объектов в `tables`
    -> REVIEW (kind="TABLES_MISSING"). Замер: 16 PASS-файлов, среди них КР401_2 (15
    упомянуто / 0 извлечено), КР571_2 (19/0), КР408_2 (6/0).

=== СТАТУС ПОРОГОВ (важно) ===
Все пороги этого промпта — **triage-гейты**, а не доказательство release readiness.
Они калиброваны по корпусу, но не по gold set (промпт 14 ещё не выполнен). Это значит:
файл, прошедший гейты 04, — **кандидат**, а не аттестованный документ. Формулировки в
отчётах и в release-манифесте должны это отражать (`"attested": false`, см. 06).
После промпта 14 пороги перекалибровать на gold-dev и проверить на holdout.
