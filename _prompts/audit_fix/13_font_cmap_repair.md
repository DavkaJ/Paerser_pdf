# 13. Font/cmap repair: детерминированно чинить НЕВЕРНЫЙ МАППИНГ (и только его)

> **Редакция 2.** Первая редакция обещала слишком много. Ревью справедливо указало: glyph
> mapping исправляет неверное Unicode-сопоставление конкретного глифа, но **не вернёт
> пропавшую букву** (`стеатогепатитный` -> `стетогепатитный`), **не восстановит потерянный
> пробел** (`ГЦР развивается` -> `ГЦРразвивается`) и не починит порядок текста. Эти случаи
> были у меня в тестах успеха — это была ошибка. Ниже они вынесены в чужую зону
> ответственности. И go/no-go больше не считается по «доле восстановленных глифов»: она
> бессмысленна, когда подавляющая часть глифов и так исправна.

## Два класса порчи. Font-repair владеет только первым

| | Класс A — **неверный маппинг** | Класс B — **утрата символов** |
|---|---|---|
| Что случилось | глиф в PDF правильный, `/ToUnicode` врёт про его код | символ/пробел отсутствует в content stream |
| Примеры | `Вагсе1опа`, `ВСЬС`, `T1b`→`Т1Ь`, `D37.6`→`037.6`, `6 мес.`→`б мес.`, `S01EC`→`801ЕС`, `Gx`→`Ох`, `H40.06`→`Н40.0б` | `стетогепатитный`, `мактротрабекулярный`, `ГЦРразвивается`, `и/или`→`ши` |
| Чинит | **font-repair, детерминированно** | **только OCR/визуальный канал** |
| Риск | ложная замена гомографа | галлюцинация OCR |

**Класс A доминирует** в обоих отладочных документах: TNM/UICC/BCLC, коды МКБ, ATC,
вирусологические маркеры, названия препаратов, числа — всё это неверный маппинг. Именно на
нём OCR сам ошибается (`6` читает как `б`), а font-repair даёт точный ответ, потому что
контур глифа — это факт, а не догадка.

**Класс B — не наша зона.** Он уходит в OCR-канал и в роутер (промпт 16). Обещать его
починку здесь было бы враньём.

```
Задача: восстановить текст класса A по КОНТУРАМ ГЛИФОВ. Пилот -> замер -> решение.
Требует промптов 08 (SourceSpan с кандидатами по каналам) и 02 (воспроизводимый OCR).
Зависимость: fontTools (уже в окружении, 4.60.1). Новый модуль crparser/engine/fontrepair.py.

=== ЭТАП 1. ПИЛОТ — сначала замер, потом код в пайплайне ===
Выборка: 20 документов с подтверждённой порчей (из карантина по kinds RESIDUAL_PIN /
OCR_REQUIRED / CORRUPTION; обязательно КР1_4, КР628_2, КР396_4, КР957_1, КР502_2, КР720_2,
КР609_2).

1. Извлечь встроенные шрифты (PyMuPDF `extract_font`), разобрать `fontTools.ttLib.TTFont`.
2. Определить: Type0/Identity-H, наличие `/ToUnicode`, `/CIDToGIDMap`, subset или нет.
3. Для каждого использованного глифа получить контур (glyf/CFF outline).
4. Сопоставить с эталонным шрифтом, по возрастанию сложности — брать первый рабочий:
   (а) хеш нормализованного контура (нормировать масштаб и позицию) против таблицы
       контуров эталонов (Times New Roman, Arial, Calibri, PT Sans — реально
       используемые в КР);
   (б) не найдено — растеризовать глиф и сопоставить по перцептивному хешу / IoU;
   (в) несколько кандидатов с близким score -> **гомограф, НЕ УГАДЫВАТЬ**, пометить.

=== ЭТАП 1-bis. МЕТРИКИ РЕШЕНИЯ (переписаны — это ключевая правка редакции 2) ===
«Доля восстановленных глифов» **не является метрикой**: в порченом документе большинство
глифов и так корректны, и любая реализация покажет 90%+, ничего не доказав.

Мерить на **известных повреждённых span'ах**. Их источник — три независимых списка:
  - подтверждённые дефекты аудита §4.1/§4.2 (перечень ниже, класс A);
  - точные попадания ключей `ocr_pins` в теле (39 попаданий в 9 PASS-файлах);
  - span'ы, где native и OCR **разошлись** (`provenance.disagreements` из промпта 08).

Метрики:
  - **recall** = доля повреждённых span'ов класса A, которые font-repair исправил ВЕРНО;
  - **precision** = доля замен font-repair, которые оказались верны;
  - **false substitution rate** = доля span'ов, БЫВШИХ КОРРЕКТНЫМИ, которые font-repair
    испортил. **Это самая важная метрика промпта.** Порог: <= 0.001. Инструмент, который
    чинит 90% и ломает 2% здорового текста, — вреден, и его нельзя внедрять.
  - **homograph rate** = доля глифов, отданных контексту/OCR как неоднозначные.

**Точка go/no-go:**
  - recall >= 0.80 И precision >= 0.98 И false_substitution <= 0.001 -> **GO**, канал
    становится основным для битого CID;
  - recall < 0.50 -> **NO-GO**, честно закрыть промпт, опереться на OCR (15/16);
  - между — частичное GO: только для однозначных глифов, остальное в OCR.
Отчёт: `_corpus/fontrepair_pilot.md`. **Не начинать интеграцию до отчёта.**

=== ЭТАП 2. Интеграция (только при GO) ===
- `fontrepair.py`: `repair_page(page) -> list[SourceSpan]` — добавляет кандидата
  `"font_repair"` к существующим span'ам. **Не заменяет native, не удаляет OCR.**
  Выбор канала — задача роутера (16), не этого модуля.
- Гомографы: разрешать по контексту (словарь терминов: BCLC, PD-L1, HBsAg, TNM, коды ATC/МКБ,
  названия препаратов) + сверка с OCR-кандидатом. Расхождение -> `confidence: low`,
  span попадает в `disagreements`. **Молча не выбирать.**
- Замерить: сколько срабатываний `ocr_pins` остаётся ПОСЛЕ font-repair. Резкое падение —
  подтверждение, что словарь пинов лечил симптом.

=== ГРАНИЦЫ ===
- Новый модуль. Правки parser.py/pdf_reader.py — минимальные (подключение канала).
- НЕ трогать: segmenter, tables, validate, схему (канал уже есть из промпта 08).
- НЕ удалять OCR. Font-repair — первый канал для класса A, OCR остаётся для класса B и

- НЕ заменять символ при неоднозначном кандидате. Пометить лучше, чем угадать.
- **НЕ обещать класс B.** Пропавшие буквы, склейки, пробелы — не сюда.

=== ДЕРЕВО РЕШЕНИЙ — go/no-go решает АГЕНТ, не человек ===

**Р1. Знаменатель для метрик — НЕ только 24 028 расхождений.**
Замер промпта 08/09 показал: гибрид-OCR **слеп внутри таблиц по построению** — из 438 537
спанов внутри bbox таблиц OCR-кандидат есть у **82** (0.02%). Слияние идёт по кириллическим
якорям, а ячейка `1А ⇥ Т1а ⇥ N0 ⇥ МО` якорей не содержит.
Значит 24 028 — **нижняя граница по телу**, а порча в таблицах в них не попала вовсе.
Знаменатель строить из трёх источников:
  - зафиксированные расхождения native/OCR (`_corpus/native_ocr_disagreements.jsonl`);
  - **спаны внутри таблиц без OCR-кандидата** (438 455) — там порча невидима детекторам;
  - попадания пинов и mixed-script в теле.

**Р2. Go/no-go — по правилу, решать САМОСТОЯТЕЛЬНО:**
- `recall >= 0.80` И `precision >= 0.98` И `false_substitution <= 0.001`
  → **GO.** Интегрировать как канал `font_repair`, полный регресс, идти дальше.
- `recall < 0.50`
  → **NO-GO.** Закрыть промпт честно, записать в INVARIANTS, **сразу идти к 13b**.
  Это валидный исход, а не провал. Не спрашивать разрешения.
- Между
  → **частичное GO:** применять только к однозначным глифам, гомографы отдавать в 13b.
- `false_substitution > 0.001` при любом recall
  → **NO-GO безусловно.** Инструмент, ломающий здоровый текст, не внедряется, каким бы
  высоким ни был recall.

**Р3. Класс B — НЕ зона 13. Тесты на него писать запрещено.**
`стетогепатитный`, `мактротрабекулярный`, `ГЦРразвивается`, `и/или`→`ши` — это утрата
символов, font-repair их не вернёт. Они остаются открытыми после 13, и это **ожидаемо**.
Их владелец — 13b (eng-OCR по кропу) и 16 (роутер).

**Р4. Таблицы после 13.** Если font-repair работает на уровне cmap документа, он чинит и
таблицы тоже (глифы одни и те же). Проверить на КР1_4 Table 1: `ШСС`→`UICC`, `Т1а`→`T1b`.
- Починилось → отлично, это снимает часть работы с 13b.
- Не починилось (гомографы) → отдать в 13b, не биться.
```
