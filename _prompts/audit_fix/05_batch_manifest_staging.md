# 05. Batch: staging, манифест прогона, транзакционная публикация

> **Редакция 2.** Первая редакция смешивала два разных понятия — «прогон технически
> состоялся» и «результат достаточно хорош» — и из-за этого её тесты противоречили друг
> другу (публиковать 722 файла при ненулевом exit; при CRASH и не публиковать ничего, и
> удалить старый JSON упавшего документа). Ниже они разведены явно.

**Доказательства из кода (проверены построчно, `batch_report.py`).**

- Ошибка записи JSON только ставит `write_ok = False` — и **валидация продолжается по
  объекту в памяти**. Отчёт опишет документ, которого нет на диске.
- При `Exception` создаётся `Report` с `CRASH`, но **старый JSON не инвалидируется**.
- `_integrity_check()` проверяет ровно одно: что существующие `outout/*.json` читаются
  через `json.load`. Не сверяет ожидаемое множество, не проверяет хеши и свежесть.
  Устаревший JSON от прошлого прогона проходит эту проверку идеально.
- `failed_write` печатается и **не влияет на exit**: `return _integrity_check()`.

---

## Две независимые оси. Их нельзя смешивать

| | Что означает | Что блокирует |
|---|---|---|
| **`run_integrity_ok`** | прогон технически состоялся: ожидаемое множество обработано, каждая запись на диск удалась, хеши сходятся, пины не менялись | **публикацию сырого `outout/`** |
| **`quality_gate_ok`** | результат достаточно хорош: нет FAIL, нет REVIEW | **release-экспорт для обучения** (промпт 06) |

`outout/` — это **сырой выход**, а не обучающий корпус. Наличие REVIEW в корпусе — норма:
мы для того и вводим гейты, чтобы их видеть. Поэтому REVIEW **не должен** блокировать
публикацию сырого выхода. Он блокирует ровно одно — попадание документа в `release/`.

А вот **сбой инфраструктуры** (не смогли записать файл) означает, что мы не знаем, что
лежит на диске, — и тогда публиковать нельзя ничего.

**Ключевое различие, которого не было в первой редакции:**

- **WRITE_FAILED** = сломана инфраструктура (диск, права, место). Мы не можем доверять
  состоянию staging. -> `run_integrity_ok = False` -> **публикации нет вообще**,
  `outout/` не тронут, exit 2.
- **CRASH** = этот конкретный PDF не парсится. Инфраструктура цела, остальные 721 документа
  корректны. -> `run_integrity_ok` **остаётся True**; документ получает статус FAIL(CRASH),
  его staging-выхода нет, и при публикации **его устаревший JSON удаляется из `outout/`**
  (он описывает результат, которого больше не существует). Документ уходит в карантин.

```
Задача: сделать публикацию батча транзакционной с ЯВНОЙ state machine. Правки только в
batch_report.py (+ использование manifest.py). Парсер и валидатор НЕ трогать.

=== ПРАВКА 1. Run-scoped staging ===
- `run_id` = UTC-таймстемп + короткий hash кода (из `manifest.code_fingerprint()`).
  Детерминированность: при одинаковом коде и входах run_id различается только временем —
  это нормально; воспроизводимость обеспечивают хеши, а не сам id.
- Воркеры пишут в `_runs/<run_id>/staging/<base>.json` (атомарно: temp + fsync + os.replace).
- `outout/` обновляется ТОЛЬКО на шаге публикации.
- `_runs/` — в .gitignore. Флаг `--keep-runs N` (по умолчанию 2).

=== ПРАВКА 2. Валидировать то, что записано ===
Порядок для каждого документа СТРОГО такой:
    parse -> write to staging -> RE-READ from staging -> validate прочитанное
Валидировать объект из памяти запрещено. Это ловит и порчу при сериализации, и рассинхрон
«отчёт про одно, файл про другое».
Статусы документа:
  - запись не удалась            -> WRITE_FAILED  (влияет на run_integrity)
  - парсинг упал                 -> FAIL(CRASH)   (НЕ влияет на run_integrity)
  - таймаут                      -> FAIL(TIMEOUT) (НЕ влияет на run_integrity)
  - записан и провалидирован     -> PASS / REVIEW / FAIL по валидатору

=== ПРАВКА 3. Манифест прогона ===
`_runs/<run_id>/run_manifest.json`:
    {
      "run_id": ..., "started_at": ..., "finished_at": ...,
      "code": {...}, "env": {...}, "config": {...},
      "pins_sha256_before": ..., "pins_sha256_after": ...,
      "expected": ["КР1_4", ...],
      "documents": {"КР1_4": {"input_sha256": ..., "output_sha256": ...|null,
                              "status": "PASS", "kinds": [...], "secs": 12.3}},
      "run_integrity_ok": true|false,
      "integrity_failures": ["WRITE_FAILED: КРxxx", "SET_MISMATCH: ...", "PINS_CHANGED"],
      "quality_gate_ok": true|false,
      "counts": {"pass": N, "review": N, "fail": N, "crash": N, "write_failed": N}
    }

`run_integrity_ok = False`, если выполнено ХОТЬ ОДНО:
  - есть WRITE_FAILED;
  - множество ключей `documents` != `expected`;
  - `pins_sha256_before != pins_sha256_after` (после промпта 02 пины immutable);
  - интеграл-чек staging нашёл нечитаемый JSON;
  - **OCR требовался, но недоступен** (см. правку 3-bis).
CRASH и TIMEOUT в этот список НЕ входят.

=== ПРАВКА 3-bis. OCR — объявленное предусловие прогона, а не удача среды ===
**Найдено при исполнении промпта 00.** `_resolve_tesseract()` (`ocr.py:225-227`) при
отсутствии `TESSERACT_CMD` откатывается на захардкоженный путь `~/Tesseract-OCR/`.
А `parser.py:_full_ocr` при недоступном OCR делает:
    if not recoverer.available(): return []   # «тихо, поведение как без OCR»
Следствие, проверяемое из кода: **на машине без Tesseract батч молча производит ДРУГОЙ
корпус и завершается с exit 0.** Доказано: у КР1_4 хеш записей оглавления при OCR-off —
`d9db4b7bf82e`, при OCR-on — `a193891de9ee`. Разные документы, одинаковый «успех».
Это последняя дыра fail-open: промпт 03 закрыл валидатор, но не окружение.

Что сделать:
  - в run_manifest писать `"ocr": {"required": true|false, "available": true|false,
    "version": "...", "traineddata_sha256": {...}}`;
  - CLI-флаг `--require-ocr` (по умолчанию **включён** для полного прогона корпуса):
    OCR требуется, недоступен -> `run_integrity_ok = False`, exit 2, публикации НЕТ.
    Отключать можно только явно (`--no-require-ocr`) — и тогда это ЗАПИСЫВАЕТСЯ в манифест,
    а `release.py` (промпт 06) такой прогон в релиз не пускает;
  - убрать молчаливый фолбэк на захардкоженный путь: путь берётся из `TESSERACT_CMD`/
    `TESSERACT_PATH` или из PATH. Не найден -> явная ошибка с внятным сообщением, а не
    угадывание домашней директории;
  - `manifest --verify` уже сверяет `env.tesseract` (после 01b) — расхождение версии или
    traineddata обязано поднимать флаг расхождения.

`quality_gate_ok = (counts.fail == 0 and counts.review == 0 and counts.crash == 0)`.

=== ПРАВКА 4. Публикация — одна явная функция ===
    def publish(run_id) -> None:
        # вызывается ТОЛЬКО при run_integrity_ok
        # 1. скопировать все staging/*.json -> outout/
        # 2. удалить outout/<base>.json для каждого base из expected, у которого
        #    НЕТ staging-выхода (CRASH/TIMEOUT) — устаревший результат не должен пережить
        #    прогон, в котором документ упал. Каждое удаление — в лог.
        # 3. удалить outout/*.json, которых нет в expected (артефакты прошлых прогонов).
        #    ТОЛЬКО при полном прогоне. При частичном (список файлов в argv) — не трогать.
Публикация НЕ зависит от `quality_gate_ok`. REVIEW и FAIL публикуются в сырой `outout/` —
это честный результат прогона, и он нужен для карантина и разбора.

=== ПРАВКА 5. Exit-коды (три состояния, не два) ===
    0  — run_integrity_ok И quality_gate_ok
    1  — run_integrity_ok, но есть FAIL/REVIEW/CRASH (публикация СОСТОЯЛАСЬ)
    2  — run_integrity_ok == False (публикации НЕ БЫЛО, outout/ не тронут)
Флаг `--allow-not-pass` превращает 1 в 0 (для локальной отладки). На код 2 он не влияет
никогда.
CI/оператор различает: «2 — чинить инфраструктуру», «1 — разбирать качество».

=== ПРАВКА 6. Воркеры и OCR-очередь ===
- `max_workers=14` -> `--workers`, по умолчанию `min(os.cpu_count(), 8)`.
- Два прохода: сначала не-OCR документы широким пулом, затем OCR-кандидаты узким
  (`--ocr-workers`, по умолчанию 2-4) — растры 400 DPI держат память.
- `--timeout` (по умолчанию 900 с) -> FAIL(TIMEOUT), а не зависший пул.

=== ПРАВКА 7. Параметризация путей (для параллельных дорожек) ===
`OUTOUT`, `REPORT` и путь OCR-кэша — из хардкод-констант в CLI/env
(`CR_OUTOUT`, `CR_REPORT`, `CR_OCR_CACHE`) со ВСЕМИ текущими значениями по умолчанию.
Поведение по умолчанию не меняется. Это позволяет двум агентам работать в разных
worktree, не деля один `outout/`.
```
