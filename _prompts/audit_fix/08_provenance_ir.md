## Модель: три уровня, и это принципиально

**1. `SourceSpan` — неизменяемая единица источника.** Существует независимо от того, кто
и как её потом прочитал. Якорится **геометрически**, а не по индексу:

```python
span_uid = "p{page}_{sha1(f'{x0:.1f},{y0:.1f},{x1:.1f},{y1:.1f}')[:8]}"
```

Геометрический якорь решает ровно ту проблему, на которую указало ревью: native-строка и
OCR-строка, покрывающие одну и ту же область страницы, — это **один span с двумя
кандидатами**, а не два несопоставимых объекта. Сопоставление при разной нарезке — по IoU
(порог `SPAN_MATCH_IOU`, старт 0.6; калибровать на реальных страницах).

**2. Кандидаты.** У span'а несколько представлений текста — по одному на канал:

```python
@dataclass(frozen=True)
class SourceSpan:
    span_uid: str
    page: int
    bbox: BBox
    candidates: Mapping[str, str]     # {"native": "Вагсе1опа", "ocr": "Barcelona"}
    confidence: Mapping[str, float]   # {"ocr": 0.91}
    selected: str                     # какой канал выбран: "native" | "ocr" | ...
```

**Ни один канал не удаляет чужой текст.** Он добавляет своё мнение. Это и есть тот
инвариант, отсутствие которого дало отказ «грязный native признан авторитетным и не заменён
правильным OCR» — сейчас альтернативы просто негде хранить.

**3. Ownership.** Кто присвоил span: секция, таблица или excluded-элемент. Ровно один
владелец. Дубли и потери становятся арифметикой, а не догадкой.

=== ШАГ 2. Ownership для ВСЕХ трёх потребителей ===
- `Section` получает: `section_id: str|None`, `page: int`, `bbox: BBox`,

  Сериализуется в JSON как объект с ТЕМИ ЖЕ полями `title`/`text` (обратная совместимость)
