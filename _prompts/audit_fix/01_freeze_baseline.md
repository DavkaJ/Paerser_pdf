# 01. Заморозить текущий прогон: манифест хешей + baseline

**Зачем первым.** Аудит (§3.2, «Ограничения») установил: `_corpus/report.json` датирован
9 июля, а `КР1_4.json`, `КР628_2.json`, `ocr.py`, `ocr_pins.json` менялись позже. Report не
хранит ни hashes входов/выходов, ни версию кода. **Сейчас нельзя доказать, что 722 JSON в
`outout/` получены тем кодом, который лежит в репозитории.** Пока это так, любая последующая
правка неизмерима: мы не сможем отличить «мой фикс изменил файл» от «файл и так был другой».

Промпт ничего не чинит. Он делает состояние измеримым. Код парсера не трогается вообще.

---

```
Задача: сделать текущее состояние корпуса воспроизводимо измеримым. Никакой логики
парсинга/валидации НЕ менять. Только новый инструмент снятия и сверки манифеста.

=== ЧТО СДЕЛАТЬ ===

1) Новый модуль `crparser/engine/manifest.py` (или `tools/manifest.py`, на твой выбор,
   но вне engine-пайплайна — он не должен вызываться из parse()).
   Функции:
   - sha256_file(path) -> str
   - code_fingerprint() -> dict: {git_sha, git_dirty: bool, tree_sha256}
       tree_sha256 — sha256 от отсортированного списка (относительный путь, sha256)
       всех *.py в crparser/ + validate.py + batch_report.py. Так фиксируется код даже
       при грязном рабочем дереве.
   - env_fingerprint() -> dict: версии python, PyMuPDF (fitz), pdfplumber, Pillow,
       pytesseract, и вывод `tesseract --version` (первая строка) + список traineddata
       с их sha256 (rus.traineddata, eng.traineddata), если найдены. Недоступное —
       None, НЕ падать.
   - build_manifest(raw_dir, out_dir) -> dict

2) Формат `_corpus/baseline_manifest.json`:
   {
     "generated_at": "<ISO8601 UTC>",
     "code": {...code_fingerprint()},
     "env": {...env_fingerprint()},
     "config": {"ocr_dpi": <из ocr.py>, "max_workers": <из batch_report.py>,
                "cov_fail": <из validate.py>, "cov_warn": ...},
     "pins_sha256": "<sha256 crparser/data/ocr_pins.json>",
     "registry_sha256": "<sha256 xlsx-реестра>",
     "inputs":  {"КР1_4": {"sha256": "...", "bytes": N, "pages": M}, ...},   # все PDF в data/raw
     "outputs": {"КР1_4": {"sha256": "...", "bytes": N, "mtime": "..."}, ...}, # все JSON в outout
     "report_sha256": "<sha256 _corpus/report.json>",
     "counts": {"inputs": 722, "outputs": 722, "pass": 616, "fail": 58, "review": 48}
   }
   `pages` брать через PyMuPDF (page_count) — это дёшево и даёт независимую сверку
   с заявленными в аудите 57 681 страницами.

3) CLI: `python -m crparser.engine.manifest --snapshot` пишет baseline_manifest.json.
   `python -m crparser.engine.manifest --verify` сверяет ТЕКУЩЕЕ состояние с манифестом
   и печатает расхождения по группам:
     - входы изменились/пропали/добавились;
     - выходы изменились/пропали/добавились;
     - код изменился (git_sha / tree_sha256);
     - pins/registry изменились.
   Exit 0 только при полном совпадении, иначе 1.

4) ВЫВЕСТИ ИЗ ОБРАЩЕНИЯ УСТАРЕВШИЙ ОТЧЁТ. `_corpus/FINAL_REPORT.txt` прямо противоречит
   текущему report.json: он утверждает 623/700 PASS и 77 FAIL (строки 4-9), считает 21 скан
   необработанным (19-20) и объявляет КР875_1 как PASS (23), тогда как его текущий статус —
   REVIEW. Файл вводит в заблуждение любого, кто его откроет.
   Действие: переименовать в `_corpus/FINAL_REPORT.OBSOLETE.txt` и добавить в начало шапку:
   «УСТАРЕЛО на <дата>. Отчёт относится к неизвестному прогону, не воспроизводим, содержит
   числа, противоречащие _corpus/report.json. Актуальный источник истины —
   _corpus/baseline_manifest.json и _corpus/report.json.» Не удалять (это история проекта).

5) ОТДЕЛЬНО: `--drift` — отчёт по расхождению отчёта и файлов. Для каждого файла из
   report.json проверить, что соответствующий outout/*.json существует и что его mtime
   НЕ ПОЗЖЕ mtime report.json. Список «выход новее отчёта» напечатать явно — это ровно
   тот дефект, который нашёл аудит (КР1_4, КР628_2). Ожидаемо непусто — это НЕ ошибка
   инструмента, это находка.

=== ГРАНИЦЫ ===
- НЕ трогать: parser.py, segmenter.py, tables.py, ocr.py, validate.py, clinical.py,
  stats.py, jsonio.py — ни строки.
- batch_report.py трогать НЕЛЬЗЯ в этом промпте (его чинит 05).
- Манифест не участвует в парсинге и не влияет на выход.
- Не перезапускать корпус. Снимаем состояние КАК ЕСТЬ, вместе со всеми его дефектами.

=== ТЕСТЫ-ПИНЫ ===
- `--snapshot` отрабатывает на 722 входа и 722 выхода, counts.pass == 616,
  counts.fail == 58, counts.review == 48 (сверка с текущим report.json).
- Сумма inputs[*].pages по корпусу печатается; ожидается ~57 681 (±, если реестр PDF
  менялся — доложить точное число, не подгонять).
- `--verify` сразу после `--snapshot` даёт exit 0 и «расхождений нет».
- Искусственно тронуть один байт любого JSON -> `--verify` даёт exit 1 и называет
  ровно этот файл. Вернуть файл — снова exit 0.
- `--drift` печатает непустой список «выход новее отчёта» и в нём есть КР1_4 и КР628_2.
- Дополнительно снять факт по уже отгруженным папкам: сколько файлов реально лежит в
  `outout_pass/` и `outout_extra_usable/` и совпадает ли множество `outout_pass/` с
  множеством PASS из report.json. (Проверено: в `outout_pass/` **596** файлов, не 616;
  21 PASS отсутствует, а КР875_1 присутствует при статусе REVIEW. Это НЕ ошибка
  инструмента — это находка, её надо зафиксировать в манифесте.)
- `_corpus/FINAL_REPORT.txt` переименован и снабжён шапкой «УСТАРЕЛО».
- Ни один файл в outout/ и ни один .py в crparser/ не изменён этим промптом
  (git status показывает только новые/переименованные файлы).

=== РЕГЛАМЕНТ ===
1. Снять baseline ДО каких-либо других правок. Закоммитить baseline_manifest.json.
2. С этого момента любой промпт, меняющий выход, ОБЯЗАН приложить дельту `--verify`:
   сколько выходных файлов изменилось и почему. Неожиданно широкая дельта = регресс.
3. Коммит: «Манифест прогона: хеши входов/выходов/кода/окружения + сверка дрейфа».
```
