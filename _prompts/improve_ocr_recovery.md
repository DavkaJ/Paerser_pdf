# Доработка OCR-гибрида: ловить битую латиницу, отрендеренную «чистой» кириллицей

Тестировать ТОЛЬКО на 2 файлах (быстрая итерация): КР1_4 и ещё один §-кандидат (напр. КР628_2). НЕ гонять весь корпус.

## Проблема (подтверждено на КР1_4 после текущего OCR)
Гибрид восстанавливает латиницу только в строках, где есть «битый токен» = «§ в токене» ИЛИ кириллица+латиница в одном слове (`_is_broken_token`, ocr.py:87-89). Но большая часть битой латиницы отрендерена в ТОКЕНЫ ЦЕЛИКОМ ИЗ КИРИЛЛИЦЫ-двойника — без «§» и без смешения скриптов:
- `ВСЬС`=BCLC (во всех местах), `Нераббз … У1гиз`=Hepatitis … virus, `СЫЫ/СЫШ`=Child, `Риф`=Pugh, `апб-НСУ`=anti-HCV, `АЬВ1, АЬЬшшп-ВШгиЫп`=ALBI, Albumin-Bilirubin, `Ю0х109`=100×10⁹, `НВзАд`=HBsAg (в части мест).
Строки с такими токенами (без §-соседа) не проходят `_is_broken_token` → НЕ отправляются в OCR → мусор выживает. Отсюда непоследовательность: «Hepatitis B virus» починился (на строке был §-токен НВзА§), а «Hepatitis C virus» на соседней строке — нет.

`merge_line` (ocr.py:111-130) уже корректен: выравнивает по кириллическим якорям, несовпавшее берёт из OCR (там латиница), настоящую кириллицу сохраняет. Значит достаточно ПРАВИЛЬНО ОТОБРАТЬ строки в OCR — слияние доделает.

## Что сделать (узко, в ocr.py)
Расширить отбор строк для OCR в `hybrid_recover`: в документе-КАНДИДАТЕ (`is_hybrid_candidate`==True по §-плотности) прогонять через OCR НЕ только строки с §/мешаниной, а ВСЕ текстовые строки (содержащие буквы). Батч-лента per-страница (`_strip_ocr`) и `merge_line` остаются как есть — merge защитит чистую кириллицу (совпавшие по кириллическому ключу токены берутся из слоя, несовпавшие — из OCR).

Опционально (если полный прогон строк по кандидату слишком медленный) — оставить быстрый отбор, но расширить `_is_broken_token`/отбор строки на «псевдо-латинские» кириллические токены: soft/hard-знак или Ы внутри всезаглавного кластера (ВСЬС, СЫШ), цифра, впаянная между кириллическими буквами (У1гиз, Ю0, АЬВ1), латиница-двойник в скобочных/аббревиатурных контекстах. Но приоритет — простой и надёжный путь: OCR всех строк кандидата + существующий merge.

## ГРАНИЦЫ
- Расширение применять ТОЛЬКО к документам-кандидатам (`is_hybrid_candidate`). Чистые файлы (без §-плотности) НЕ трогать — ни OCR, ни замедления, вывод прежний.
- `merge_line` не менять (он уже безопасно сохраняет чистую кириллицу; менять только ОТБОР строк).
- Не трогать структуру разделов/таблицы/детекторы; выход — та же схема; graceful fallback при отсутствии Tesseract/rus.
- Без хардкода конкретных строк/имён.
- Стоимость: OCR всех строк кандидата ≈ полностраничный OCR ДЛЯ ЭТИХ ФАЙЛОВ (их ~десятки, не весь корпус) — приемлемо; чистых 570+ это не касается.
